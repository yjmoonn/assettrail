기준일: 2026-08-07

이 문서는 AssetTrail을 자산 기록 도구에서 투자 의사결정 운영체계로 확장하기 위한
활성 작업 목록이다. 구현 진행 상황은 이 문서의 체크박스와 단계 상태표를 기준으로
관리한다.

## 상태와 우선순위 기준

- `[ ]`: 대기 또는 진행 중인 작업
- `[x]`: 구현과 필수 검증이 모두 끝난 작업
- `기반 1순위`: 다른 분석 기능의 정확성을 좌우하는 데이터 기반
- `빠른 1순위`: 기존 데이터로 먼저 제공할 수 있는 높은 효용의 기능

## 기능 우선순위와 구현 단계 매핑

| 구현 단계 | 상태 | 매핑되는 추천 기능 | 선행조건 |
|---:|---|---|---|
| 1 | 완료 | 투자 의사결정 센터, 기본 집중도 분석 | 없음 |
| 2 | 완료 | 신규자금 배분 도우미, 수동 실질노출·위험 지도 | 1단계 자산 역할·목표 정보 |
| 3 | 완료 | 거래·현금흐름 원장, CASH 자동 정산 | 1단계부터 데이터 모델 사전 설계 |
| 4 | 완료 | 증권사 CSV, TWR·XIRR, 성과 원인 분석 | 3단계 거래 원장 |
| 5 | 로컬 기반 완료·공급자 대기 | ETF 실질노출, 기업 데이터, 보안형 AI 보고서 | 1~4단계의 구조화된 데이터 |

거래·현금흐름 원장은 중요도 기준으로 `기반 1순위`지만 데이터 마이그레이션 범위가

설계는 1단계부터 병행한다.

## 3단계 — 거래·현금흐름 원장

목표: 자산 변화와 외부 현금흐름을 분리해 정확한 잔액과 향후 성과 분석의 기반을
만든다.

### 원장 모델

- [x] `BUY`, `SELL`, `DEPOSIT`, `WITHDRAWAL`, `DIVIDEND`, `INTEREST`, `FEE`, `TAX`,
  `SPLIT`, `VALUATION`, `FX` 이벤트를 정의한다.
- [x] 이벤트에 거래일, 결제일, 수량, 가격, 통화, 거래 당시 환율, 비용, 계좌와
  원본 식별자를 보존한다.
- [x] 기존 보유 자산은 매수 이력을 추정하지 않고 명시적인 기초잔액 이벤트로
  마이그레이션한다.
- [x] 이벤트를 `users/{uid}/financeData/primary/ledgers/{ledgerId}/events/{eventId}`
  세대별 하위 컬렉션에 저장해 단일 문서 크기 제한을 피한다.
- [x] 로컬 저장, 클라우드 동기화, 내보내기·가져오기와 충돌 해결 방식을 설계한다.

### 현금 정산과 정합성

- [x] 매수·매도 시 결제 CASH 계좌를 선택하게 한다.
- [x] 매수는 현금을 차감하고 매도는 비용·세금을 반영한 순현금을 증가시킨다.
- [x] 배당·이자·입출금이 자산 총액과 현금흐름 분류에 함께 반영된다.
- [x] 거래 수정·취소는 원본을 조용히 덮어쓰지 않고 감사 가능한 방식으로 처리한다.
- [x] 기초잔액만 있는 오등록 종목·자산은 정정·취소 이벤트를 남겨 안전하게 복구한다.
- [x] UI 등록과 가져오기에서 중복 자산 identity·중복 ID를 반영 전에 차단한다.
- [x] 포지션 수량, 평균단가, 현금 잔액과 이벤트 합계의 정합성을 검사한다.

### 완료 기준

- [x] 매수·매도 후 주식과 현금 변화가 하나의 작업으로 일관되게 저장된다.
- [x] 기존 사용자 데이터 마이그레이션 전 자동 백업과 실패 시 복구가 동작한다.
- [x] 900KB 사용자 문서 방어와 여러 기기 revision 충돌 처리가 유지된다.
- [x] 데이터·클라우드·Firestore Rules 전체 테스트가 통과한다.

현재 일상 화면은 매수·매도, 입출금·배당·이자·수수료·세금과 MANUAL 평가조정을
지원한다. `SPLIT`과 `FX`는 계산 엔진과 가져오기 스키마에는 정의되어 있지만 직접
입력하는 일상 화면은 후속 작업으로 남긴다. 원장 기준일 이전의 `realizedTrades`는
현재 보유를 이중 차감하지 않도록 SELL 이벤트로 소급 재생하지 않는다. 기존 US
기초잔액의 과거 환율도 추정하지 않으므로 해당 구간의 원화 원가·성과는 미확정이다.

## 4단계 — 정확한 성과 측정

목표: 신규 입출금과 투자 결과를 분리하고, 성과가 발생한 원인을 설명한다.

### 증권사 CSV

- [x] 증권사별 CSV 어댑터를 독립 모듈로 정의한다.
- [x] 가져오기 전에 거래 수, 기간, 계좌, 예상 변경을 미리 보여준다.
- [x] 원본 거래 ID와 보조 키를 이용해 중복 가져오기를 차단한다.
- [x] 일부 행 오류 시 전체 교체 대신 오류 행과 처리 결과를 보고한다.
- [x] 개인 식별 정보가 로그나 오류 보고서에 남지 않게 한다.

### 성과와 원인 분석

- [x] TWR과 XIRR을 계산하고 각 지표의 적용 범위를 설명한다.
- [x] 자산 증감을 신규 입출금, 잔여 투자효과(추정), 환율, 배당·이자,
  수수료·세금의 가치변화 브리지로 나눈다.
- [x] 기간별 벤치마크 대비 성과를 제공한다.
- [x] 최대 낙폭, 회복 기간과 변동성을 제공한다.
- [x] 거래 원장 이전의 과거 스냅샷은 `자산 변화`로 표시하고 투자수익률로 소급
  추정하지 않는다.

### 완료 기준

- [x] 입출금이 있는 검증 포트폴리오에서 TWR·XIRR 기준값과 일치한다.
- [x] 가치변화 브리지 합계가 비용과 반올림 허용범위 안에서 총 변화와 일치한다.
- [x] 동일 CSV를 반복 가져와도 거래가 중복 생성되지 않는다.
- [x] 계산 단위 테스트, 가져오기 실패 테스트와 기간별 UI 검증이 통과한다.

4단계의 내장 가져오기 형식은 AssetTrail 표준 거래 CSV v1이다. 엔진·어댑터 경계는
개별 증권사 양식을 추가할 수 있게 분리했지만, 증권사 원본 파일을 모두 직접 지원하는
것은 아니다. CSV 원문은 미리보기 동안 메모리에만 두며 파일은 15MB·50,000행,
기존 이벤트를 포함한 전체 원장은 50,000건으로 제한한다.

성과는 스키마 v6의 `performanceObservations`에 저장된 검증 평가점부터 계산한다.
과거의 단순 `snapshots`는 소급 사용하지 않으므로 운영 환경에서는 서로 다른 날짜의
평가점이 앞으로 쌓여야 기간 성과가 보인다. 입출금일 평가점이 빠지면 TWR은 차단하고
XIRR만 실제 현금흐름 날짜로 계산한다. KOSPI와 S&P 500 비교는 배당 제외 가격지수이며,
S&P 500은 평가일 USD/KRW로 원화 환산한 비헤지 비교다.
현재 평가점은 클라우드 주 문서의 900KB 안전 여유를 위해 300개까지 보존한다. 한도에
도달하면 기존 점을 보존하고 새 날짜 생성 중단을 명시적으로 안내한다. 장기 이력은
별도 하위 컬렉션이 필요하다. 가격 evidence fingerprint는 생성 당시 근거의 128-bit
digest이며 과거 시세 원본을 독립 재조회한 감사 증명으로 사용하지 않는다.

## 5단계 — 외부 데이터와 AI

목표: 실제 경제적 노출과 기업 상태를 보강하고, 검증 가능한 계산 결과를 AI가
설명하도록 한다.

### 외부 데이터

- [x] 미국 종목을 안전하게 등록·검토해 가격 대상에 추가하는 운영 흐름을 만든다.
- [x] Butler 공식 화면에서 사용자가 복사한 표를 확정치·컨센서스가 분리된 기업 사실로
  정규화하고 출처를 `BUTLER_MANUAL`·`USER_SUPPLIED`·`SECONDARY_AGGREGATOR`로 남긴다.
- [x] 출처 조회 시각을 필수로 검증하고 5분을 초과한 미래 조회 시각과 조회일보다
  미래인 확정치는 거부하되 미래 컨센서스는 예상치로 보존한다.
- [x] Butler 붙여넣기 원문은 메모리에만 두며 자동 로그인·스크래핑·비공개 API와 세션
  쿠키 재사용을 하지 않는다.
- [x] 사용자 제공 또는 재배포 허용 ETF 카탈로그의 출처, 기준일, 커버리지와 재배포

### 완료 기준

- [x] ETF 노출 합계, 기준일과 미매핑·미보고·미지원 비중을 사용자가 확인할 수 있다.

- [x] 사용자 전환 시 외부 입력·AI 결과 화면 상태를 지우고 사용자별 분석 저장 키를
  회귀 테스트로 확인한다.
- [ ] 다른 사용자의 분석 데이터와 보고서에 접근할 수 없음을 E2E로 검증한다.

로컬 안전 기반은 위 완료 항목의 범위다. 기업 스냅샷과 ETF 카탈로그는 로그인 사용자의
주 v6 문서·Firestore와 분리된 사용자별 로컬 키에만 보관한다. 따라서 클라우드 분석
데이터의 사용자별 E2E는 자동 백엔드와 저장소를 실제로 추가할 때 완료해야 한다.
